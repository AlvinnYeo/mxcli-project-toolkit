# mxcli-project-toolkit 1.0

**What it is.** A shared process layer for building and changing Mendix apps with an AI coding
agent and [mxcli](https://github.com/mendixlabs/mxcli). It gives the agent a staged pipeline
with recorded decisions (`PROJECT.md`), skills it loads only when a task calls for them, and
mechanical gates (`bin/gate-check.sh`, lint, mxbuild, end-to-end journeys) that report what is
actually in your project. It runs for migrations, requirements-driven builds, greenfield builds
and changes to a live app, or à la carte to audit and test an app you already have.

1.0 is the first named milestone on top of the release train. It is not a rewrite: these notes
pick out what changed in the two weeks before it (2026-09-30 to 2026-10-14). Every line traces to
an entry in [`CHANGELOG.md`](../../CHANGELOG.md), which has the full detail and field evidence.
How milestones relate to the `vYYYY.MM.DD` tags: [`docs/RELEASE-PROCESS.md`](../RELEASE-PROCESS.md)
§8.

1.0 is the first release-train tag published to GitHub, cut with `bin/cut-release.sh` when this
release is announced. Earlier `vYYYY.MM.DD` headings in CHANGELOG were never pushed as tags.

Most PRs linked below landed together through
[#329](https://github.com/MendixMau/mxcli-project-toolkit/pull/329) and show as closed on GitHub; their
changes are on master.

## Highlights

### Every merge is reviewed by someone who did not write it

A PR now gets an independent review (MERGE / MERGE-AFTER-FIX / HOLD, on value, regression risk
after sync, correctness and context cost) before it lands; green CI and the author's own report no
longer count as one. Nine PRs had merged on 2026-10-13 without one
([#316](https://github.com/MendixMau/mxcli-project-toolkit/pull/316)). Several fixes in this
release came out of those reviews (the exec lock race, the final-LOOK timing, the
`test-stack-up` exit codes).

**For you:** what reaches your project on `git pull` has been read by a second reviewer, not just
tested by its author.

### Less text in every session

The always-loaded skill tier had reached 79,997 words against an 80,000-word cap. Incident stories
moved behind pointers into `process/baseline-incident-history.md` and the tier dropped to 76,259
words with no rule removed ([#315](https://github.com/MendixMau/mxcli-project-toolkit/pull/315)).
New rule: room is made by moving text, never by deleting rules. `change-intake.md` became a
331-word core with an on-demand detail file
([#327](https://github.com/MendixMau/mxcli-project-toolkit/pull/327)), dispatch guidance moved to
its own small file ([#320](https://github.com/MendixMau/mxcli-project-toolkit/pull/320)), a
scaffolded `CLAUDE.local.md` is 17% shorter
([#292](https://github.com/MendixMau/mxcli-project-toolkit/pull/292)), routing in
`CLAUDE.local.md` carries triggers only
([#226](https://github.com/MendixMau/mxcli-project-toolkit/pull/226)), helper stubs read about 18%
less per dispatch ([#223](https://github.com/MendixMau/mxcli-project-toolkit/pull/223)), and a
build helper can get one context-pack file per build step instead of a reading list
([#198](https://github.com/MendixMau/mxcli-project-toolkit/pull/198)).

**For you:** run `bin/sync-project.sh` and existing projects pick up the shorter wiring; sessions
start with less to read.

### `exec.sh`: per-project lock, restart verdicts, safer restarts

In a 20-task field run, 57 of 148 `exec.sh` runs applied nothing, and a machine-wide guard blocked
writes because a *different* project was writing. `exec.sh` now locks per project with a stale-lock
takeover, offers an opt-in `--commit-first`, and ends every applied script with a verdict: restart
needed, watch can apply this, or unknown
([#304](https://github.com/MendixMau/mxcli-project-toolkit/pull/304),
[#324](https://github.com/MendixMau/mxcli-project-toolkit/pull/324)). The review of #304 found the
takeover could let up to three contenders hold the lock; it is now serialised, and a fixture runs
10 rounds of 12 contenders and asserts at most one holder. New `bin/app-restart.sh` (#304) restarts only
this project's own `mxcli run --local`; since
[#322](https://github.com/MendixMau/mxcli-project-toolkit/pull/322) it also refuses over a leftover `mxcli test` injection.

**For you:** two projects on one machine no longer block each other, and the agent is told when a
change needs an app restart instead of guessing.

### Lint you can trust and tune

UX001/002 plus Batches 1–4 landed: UX001/UX002, then ERR001/LOOP001, PERF001/002/004,
TXT001/TXT002/UI001, and Batch 4 with **SEC014** (an external role that can write status, audit or ownership members) and a
CONV009 that reads its `maxObjects` option
([#238](https://github.com/MendixMau/mxcli-project-toolkit/pull/238),
[#248](https://github.com/MendixMau/mxcli-project-toolkit/pull/248),
[#270](https://github.com/MendixMau/mxcli-project-toolkit/pull/270),
[#305](https://github.com/MendixMau/mxcli-project-toolkit/pull/305),
[#312](https://github.com/MendixMau/mxcli-project-toolkit/pull/312)). When `mxcli init` reverts
toolkit rules to stock, the lint gate now stops as **BLIND** instead of blaming the next script
for the jump, and sync restores them
([#308](https://github.com/MendixMau/mxcli-project-toolkit/pull/308)). Turning a rule off has one
supported route (`enabled: false` in `lint-config.yaml`, recorded in `PROJECT.md`). A metrics
ledger records outcome, speed, lint total and `mxcli report` score for every exec
([#265](https://github.com/MendixMau/mxcli-project-toolkit/pull/265)).

**For you:** SEC014 asks one question (which roles are external) and prints a NOTE until you
answer it.

### End-to-end proof that fails for the right reason

The journey runner preflights the suite (a refused admin credential aborts before the first
journey) and journeys can declare `requires` / `leaves` / `consumes`
([#302](https://github.com/MendixMau/mxcli-project-toolkit/pull/302)). OQL rows are read by SELECT
alias, an app that dies mid-suite reads APP-DOWN rather than FAIL, and negative-only claims get a
liveness reference ([#310](https://github.com/MendixMau/mxcli-project-toolkit/pull/310)).
`test-stack-up.sh` identifies this project's own `run --local` by its command line
([#319](https://github.com/MendixMau/mxcli-project-toolkit/pull/319)). Re-runs are scoped to what
a change touched, UI-only changes get a light lane, and unit tests are off by default
([#290](https://github.com/MendixMau/mxcli-project-toolkit/pull/290)). The page-fidelity scorer
matches what a page displays, on whole words
([#318](https://github.com/MendixMau/mxcli-project-toolkit/pull/318)).

**For you:** fewer false reds from the harness, and less time re-proving changes nobody touched.
**Check after upgrading:** `oqlScalar` now returns the first SELECT alias.

### Stage 3 designs how users reach each page

Stage 3 now writes `design/interaction-model.md` before the first wireframe: a home per role, an
inbox per user task, and for each page how it is reached and what it receives. Every wireframe
opens with a contract block ([#317](https://github.com/MendixMau/mxcli-project-toolkit/pull/317),
part 1 of [#291](https://github.com/MendixMau/mxcli-project-toolkit/issues/291)). Three apps had
passed every gate while one rooted 8 pages on a parameterless retrieve and gave all 6 roles one
home page.

**For you:** navigation and page-parameter defects surface at design time, when they are cheap.

### Changing an existing app: delivery rounds and mid-build changes

In change-an-existing-app mode, `bin/status.sh` reports the delivery round from a `## Rounds`
table in `PROJECT.md`, drops noise that does not apply there, and counts targeted manual Studio
Pro steps written from `templates/manual-steps.md`
([#326](https://github.com/MendixMau/mxcli-project-toolkit/pull/326)). In every mode, feedback
typed mid-build is logged as a change-log row in `PROJECT.md` before any edit, and the
requirement or design is changed before the MDL
([#306](https://github.com/MendixMau/mxcli-project-toolkit/pull/306)). A final whole-app LOOK is
now owed at Stage 6 ([#303](https://github.com/MendixMau/mxcli-project-toolkit/pull/303),
[#321](https://github.com/MendixMau/mxcli-project-toolkit/pull/321)).

**For you:** "where are we" has an answer in rounds, not a stage number that never moves.

## Upgrading

```bash
git -C ~/Mendix/mxcli-project-toolkit pull
~/Mendix/mxcli-project-toolkit/bin/sync-project.sh <project-root>
```

Skills update with the pull; sync refreshes what was copied into the project (intake questions,
untouched agent stubs, `bin/` and `tests/e2e/` copies nobody edited, lint rules). Once release tags
are published (from 1.0 on) it prints the `Toolkit release:` line you are on; before that it
prints `Toolkit release: none tagged yet`. Then:

- Answer SEC014's question (which roles are external), then re-baseline lint once, as the sync
  NOTE says.
- On mxcli v0.26 or later, sync runs a read-only property-set check (models written by mxcli up
  to v0.25 can break Studio Pro's merge). If it reports a repair is needed, run
  `bin/doctor.sh --fix-property-sets <project>`
  ([#314](https://github.com/MendixMau/mxcli-project-toolkit/pull/314)).
- Projects with per-BRD coverage ledgers: run conformance once after the upgrade; old rows are
  re-keyed ([#307](https://github.com/MendixMau/mxcli-project-toolkit/pull/307)).

## Known gaps

- **Field runs still owed.** Fixtures pass, but no real-project run is cited yet for: the
  property-set check, the page-fidelity rescoring, PROOF-OF-LOOK per section, per-BRD conformance
  ledgers, the graph-sweep catalog guard on mxcli v0.24, and the metrics ledger inside a live
  `exec.sh`.
- **[#291](https://github.com/MendixMau/mxcli-project-toolkit/issues/291) parts 2 and 3** (gate
  facts for the interaction model, and the model-side check) are not built.
- The exec stale-lock takeover can still race if a holder is killed mid-takeover. It is rare; a
  designed fix and a regression test are owed.
- `mxcli fix hashes` as an `exec.sh --patch` post-step is pending
  ([#295](https://github.com/MendixMau/mxcli-project-toolkit/issues/295)).
- No shipped pipeline writes an extraction-quality score file yet; the Stage 1 report shows that
  section as "manual".
- On Windows and Linux without Studio Pro, `exec.sh` skips its mxbuild gate unless mxbuild is
  found; run `bin/doctor.sh --install <project>` or set `MXBUILD_PATH`.
